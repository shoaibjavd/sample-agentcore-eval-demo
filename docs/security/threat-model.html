Ten of the eighteen threats are now mitigated, two are partially mitigated, and six remain open — five of which are Low severity. TS001 M2M full-tool RBAC bypass via scopes-without-roles path HighMITIGATED The blanket bypass in _should_trim() is removed. A gated tool now requires a matching role or a matching scope; tools declare auth_meta(roles=[…], scopes=["mcp/finance"|"mcp/hr"]) and the Cognito resource server defines per-domain scopes. Verified live: a token with only mcp/invoke could not reach the finance tool, while a token with mcp/finance mcp/hr could. Deny-by-default now applies to newly added gated tools.
Residual: a leaked M2M secret still reaches the domains that client is granted — bounded, not eliminated.
TS002 JWT forgery accepted by MCP due to skipped signature verification MediumMITIGATED src/auth/utils.py verifies the signature via PyJWKClient against the pool's JWKS, checks the issuer and expiry, and fails closed if USER_POOL_ID is absent or JWKS is unreachable — it never falls back to an unverified decode. Verified against a real token: valid accepted; tampered signature rejected (InvalidSignatureError); unsigned alg:none forgery rejected (PyJWKClientError).
TS003 Malicious same-repo PR tampers with agent/MCP code under CI OIDC role HighOPEN (partial) In-repo scaffolding added: the evaluate job now names an environment: dev, and all 10 actions are SHA-pinned so a repointed tag cannot inject code. Now applied in AWS: the role's trust policy is scoped to sub = repo:<owner>/<repo>:environment:dev using StringEquals, so STS issues credentials only to a job declaring that environment — it also previously trusted a different repository entirely, so it could not have been assumed from here at all. And iam:* on Resource:* is replaced by role operations scoped to the stack's own role names; verified with iam simulate-principal-policy, with iam:CreateUser, iam:CreateAccessKey, iam:PutUserPolicy and cross-role writes all returning implicitDeny. A full CI deploy then succeeded under the narrowed policy.
Still outstanding — the decisive control: required reviewers on the dev environment. The scoping is not yet a gate, because the workflow itself declares environment: dev, so any PR that triggers it yields a matching subject. The CI run proceeded without pausing, confirming no reviewer requirement is set. Blast radius is bounded; access is not yet gated. This is a GitHub setting the repository cannot enforce. Deploy-on-PR is deliberately unchanged: gating the merge on evaluation results is what this sample exists to demonstrate.
TS004 Prompt injection coerces agent into unauthorized tool invocation or header exfiltration LowOPEN (accepted) A system-prompt mitigation was implemented, then deliberately reverted after evaluation: it could not be shown to help, and prompt-level defences are weak. No Bedrock Guardrail is configured (grep for guardrail returns 0). Structural mitigations do exist and limit impact: tool access is enforced server-side by AuthMiddleware, and the agent never places the bearer token in model context.
Proper fix: attach a Bedrock Guardrail. Deferred by decision, not oversight.
TS005 Role escalation between FinanceUser and HRUser via AdminUpdateUserAttributes LowMITIGATED custom:roles is now declared immutable (cognito.StringAttribute(mutable=False)), so the claim the MCP server authorizes against cannot be rewritten after user creation. Verified in the deployed pool schema (Mutable: false on roles) with RBAC still passing 6/6. Defence in depth: the pre-token Lambda also validates roles against an allowlist.
TS007 Lateral movement via over-broad Bedrock and AgentCore IAM permissions MediumMITIGATED Three separate reductions, each confirmed on the deployed roles via iam get-role-policy: Bedrock narrowed from foundation-model/* plus account-wide bedrock:* to three exact ARNs (inference profile + model in its two routing regions, confirmed via get-inference-profile); ECR image-pull scoped to repository/* with only GetAuthorizationToken left on * where AWS requires it; and InvokeAgentRuntime scoped from account-wide agent-runtime/* to the specific MCP runtime ARN. MODEL_ID is a single constant shared by policy and runtime env so they cannot drift.
TS008 Sensitive claims and token fragments leaked via DEBUG logs LowMITIGATED LOG_LEVEL is INFO on both runtimes (grep for LOG_LEVEL": "DEBUG" returns 0). Authorization decisions are still logged for audit, but without decoded claim dumps. The remaining sub-case is now closed too: mask_error_details=True and include_traceback=False, so internal exception text and stack traces are no longer returned to callers. Errors are still logged server-side in full.
TS009 AWS account ID disclosure via Cognito domain prefix and public OAuth endpoint LowMITIGATED Domain prefix is now agentcore-<stage>-<sha256(account)[:12]> — deterministic, unique per account, non-identifying. Verified deployed: agentcore-dev-fd39890e9af3.
Residual: the historical account ID remains in git history — see the note below the table.
TS010 Denial-of-wallet via unthrottled Bedrock and AgentCore invocations MediumPARTIAL — detection only Two CloudWatch alarms added on real metrics (AWS/Bedrock Invocations > 200 and InputTokenCount > 500k per 5 min, dimensioned on the model), verified present and in OK state after deploy. This detects, it does not prevent. Both runtimes remain network_mode=PUBLIC with no rate limiting, and no notification target is wired to the alarms. Prevention requires a fronting layer (API Gateway usage plans / WAF rate rules) plus Bedrock quotas — a topology change.
TS011 Destructive removal policies on stateful/identity resources MediumMITIGATED (non-dev) _removal_policy(stage) returns RETAIN for every stage except dev. dev deliberately keeps DESTROY: the notebooks deploy and tear down repeatedly and retained pools/secrets would collide with the next deploy. Verified: synthesized template has 3 DeletionPolicy: Delete and 0 Retain at dev, as intended.
TS012 / TS013 Supply chain via mutable dependency references MediumMITIGATED All 10 workflow actions pinned to 40-character commit SHAs (semgrep p/github-actions returns 0 findings); both container base images pinned by digest (python@sha256:2c941e86…); every container dependency pinned to an exact version. Both images were rebuilt and functionally verified after pinning.
The caveat in v2 proved correct and has been acted on. A pip-audit run inside both built images found 13 distinct advisories frozen in place by the pinning: PyJWT 2.11.0 (6 advisories — the library performing the TS002 signature verification, so a vulnerable version undermined that control), bedrock-agentcore 1.4.1 (2), and pip 25.0.1 in the base image. Now PyJWT 2.13.0, bedrock-agentcore 1.18.1, pip upgraded at build; both images report no known vulnerabilities. Verified functionally: both notebooks pass on the upgraded images.
Residual: OS-level packages in the base image remain unscanned (grype/syft unavailable), and pins go stale. That last point is now addressed in CI: pip-audit runs as a security-scan step on every PR, so a future advisory in a pinned version surfaces rather than sitting frozen in the image.
TS014 Secrets in CI output & telemetry MediumMITIGATED The client secret no longer transits CI step outputs. The step that wrote it to $GITHUB_OUTPUT is removed; scripts/agentcore_eval.py resolves credentials from Secrets Manager via M2M_SECRET_ID, and the warmup step reads them with boto3 instead of interpolating a secret into a command line (where it would appear in the process list). Verified: the script's Secrets Manager path acquires a valid token with no secret present in the environment.
Strengthened further: the warmup step now uses urllib in-process rather than invoking curl, so the client secret no longer appears in the process argument list either — the earlier change had only kept it out of step outputs. Confirmed in CI, where the warmup reached the MCP server on its first attempt.
TS015 Fail-open / insecure defaults (privileged path is the default) MediumMITIGATED Both fail-open defaults are gone: the M2M authorization bypass (TS001) and the unverified JWT decode (TS002). Token verification now fails closed on any error — missing pool ID, unreachable JWKS, bad signature — rather than proceeding with unverified claims.
TS016 Authorization bypass built in as a feature HighMITIGATED Resolved with TS001. There is no longer a code path that grants all tools on the basis of holding any scope; scope grants are explicit and per-domain, declared in the CDK stack.
TS017 No security gate in the pipeline MediumPARTIAL — reports, does not gate A security-scan job was added running bandit, checkov, detect-secrets and pip-audit at pinned versions — the last covering dependency vulnerabilities, which is how the 13 advisories under TS012/TS013 were found. It carries continue-on-error: true, so a finding will not block a PR — chosen deliberately because the current findings are untriaged and a permanently red build is worse than none. Removing that one line turns it into a real gate. Note the ASH v2 scan found a 15× noise ratio from unexcluded build artifacts. The exclusions that fixed it (.ash/.ash.yaml) have since been untracked from the repository, so CI and any fresh clone will again see ~69 findings instead of 0 — measured, same code. Restoring at least the artifact exclusions is a precondition for this job being worth gating on.
TS018 Missing detection & response MediumPARTIAL Two Bedrock spend alarms exist (see TS010) and MCP now emits structured authorization audit logs (Tool execution authorized / Access denied to tool with role and scope context) — these were used as primary evidence during verification, so they are demonstrably useful. X-Ray tracing is now enabled on PreTokenFn, the function that injects the custom:roles claim — previously the authorization path's only untraced component. Still absent: any alarm on authorization failures or token rejections, no notification target on the existing alarms, and no CloudTrail or GuardDuty reference. The latter two are account/org-level controls, deliberately not enabled from this stack since the target account hosts unrelated workloads.
TS019 Trusting unverified input (no aud/iss/exp/token_use checks) HighMITIGATED Resolved with TS002. Issuer and expiry are now verified. Audience verification remains disabled by design — Cognito access tokens carry no aud claim; the platform authorizer restricts allowed_clients, and client_id is available in claims should stricter binding be wanted.
Cross-cutting residual: historical credential exposure. The fixture's AWS access key ID and account ID were removed from the working tree and GitHub branch history was rewritten (69 commits, tree hash unchanged). They remain reachable from GitHub refs/pull/1/head and refs/pull/2/head, which are read-only and can only be purged by GitHub Support, and from the Amazon remote's main and dev, where GitFarm's fast-forward-only hook blocks the rewrite and its delete-and-recreate workaround retains the old objects behind a hidden ref by design. Both values should be treated as permanently disclosed. The key is an expired ASIA temporary credential; the account ID is not itself a credential and belongs to the fixture's original author.

Prioritised recommendations

  1. Close TS003 — one setting remains. Add required reviewers to the dev environment in repository settings. The trust policy is already scoped to environment:dev and iam:* is already removed, so this is the last of the three enabling conditions and the only one the repository cannot control. Until it is set, a PR can still obtain credentials — it simply cannot escalate beyond this stack's own resources.
  2. DONE Dependency audit made recurring. The one-off pip-audit run found 13 advisories frozen by the pins, including 6 in the JWT library enforcing TS002. It is now a step in the security-scan job, so pins are audited on every PR rather than once. Still reporting only — see the gate recommendation below.
  3. Restore the scanner exclusions, then make the pipeline gate real (TS017). .ash/.ash.yaml is no longer tracked, so the noise it removed is back: 69 findings from a fresh clone versus 0 with it present. The artifact exclusions (cdk.out/, notebook output) excuse no risk and are safe to re-add; gating before that would make the job noise.
  4. Alarm on authorization failures (TS018). The audit logs already emit Access denied to tool and token-rejection events; a metric filter on those is the cheapest meaningful detection upgrade.
  5. Add a reserved-concurrency limit to PreTokenFn (CKV_AWS_115) once a safe ceiling is measured — it bounds cost and blast radius, but too low a value fails sign-ins under load.
  6. Revisit TS004 with a Bedrock Guardrail if this pattern is adapted for real tools; the prompt-level attempt was reverted for good reason.
  7. Before production: require MFA (COG2), consider Cognito Plus (COG8), and use a CMK for the M2M secret — all currently accepted for a dev demo.

How to re-verify the two authorization controls

These are the mitigations where a silent regression would be least visible, so they are worth re-testing directly rather than inferring from a passing notebook:

# TS001 — a scope must not grant a domain it does not name.
#   Request a token with only mcp/invoke, ask the agent for a stock price:
#   expected = the finance tool is NOT used. Then request mcp/finance: expected = $175.50.
#   MCP logs the decision either way ("Access denied to tool" / "Tool execution authorized").

# TS002 — forged tokens must be rejected inside the container.
docker run --rm -e USER_POOL_ID=<pool> -e AWS_DEFAULT_REGION=<region> <mcp-image> python -c "
from src.auth.utils import _decode_verified
_decode_verified('<valid token>')            # accepted
_decode_verified('<token with last 3 chars changed>')  # InvalidSignatureError
_decode_verified('<alg:none forgery>')        # PyJWKClientError
"

A note on interpreting notebook results: notebook 01's RBAC assertions read the agent's natural-language reply, so a model refusal can present as an authorization failure. During this work a 5/6 result was traced to the model declining to call a tool it was permitted to use — MCP logs showed the call authorized, and the cause was a tool docstring advertising a role requirement. Check the MCP authorization logs before concluding that RBAC has regressed.
